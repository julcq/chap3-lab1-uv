Question 1: The credentials are temporary. What happens to a running Spark job if the service is restarted mid-lab, and why?

The job is lost. A restart kills the pod, so the driver JVM, the SparkSession and everything held in memory (cached DataFrames, temp views, lineage) disappear. Local files in /home/onyxia/work are wiped too. Even without a restart, the STS credentials copied from the environment into the Hadoop configuration at session start are static and expire. Once they do, the next S3A request fails with a 403 (ExpiredToken / InvalidAccessKeyId) and the job fails, because the provider only reads fixed values and never refreshes them. After a restart, Onyxia issues new credentials, so a new session must be created from the fresh environment variables.

Question 2: Why does a plain SimpleAWSCredentialsProvider fail here, while it worked in setups without a session token?

SimpleAWSCredentialsProvider only reads the access key and the secret key. STS credentials are a triplet: access key, secret key and session token. The token must be sent with every request in the x-amz-security-token header. Without it, the object store rejects the signed request, with a 403 InvalidAccessKeyId/invalid token error. Long-lived keys work with the simple provider because they need no token. TemporaryAWSCredentialsProvider also reads fs.s3a.session.token and sends it.

Question 4: Compare the DataFrame and SQL cells above. Which one would you choose for a one-off exploration, and which for a model reused by several colleagues? Why?

Both compile to the same Catalyst plan, so performance is identical. The choice is about ergonomics. For a one-off exploration I would pick Spark SQL: it is concise, declarative, readable at a glance, and quick to type and change. For a model reused by several colleagues I would pick the DataFrame API wrapped in small named functions. It is composable and parameterizable, it can be unit-tested, and it is easier to refactor and to review in Git. Column names are Python objects rather than strings buried in a query, so editors can help. SQL stays a valid choice for a team of analysts who only know SQL, as long as the queries live in versioned files with tests, which is what dbt provides.

Question 5: regexp_extract() returned an empty string instead of NULL on no match. Where else in this notebook could that same behavior silently produce a wrong result if left unhandled?

The same call is used for state and zip_code, and only city was converted back to NULL. For an address that does not match the pattern, state and zip_code would be empty strings, not NULL. The final SQL query would then count them as a group with an empty state in GROUP BY state. A not_null check on zip_code would pass although the value is missing. A join or filter on those columns would also treat "" as a real value. The trim on text columns can create the same issue: a blank value becomes "" rather than NULL. The missing_city metric is only reliable for city, because it is the only column converted to NULL. The safest fix is to apply the empty-string-to-NULL conversion to every extracted column. Casts are another source of silent errors in non-ANSI mode, because an invalid value becomes NULL. Spark 4 enables ANSI mode by default, so there a bad cast raises an error instead.

Question 6: List the objects written under silver/users.parquet/. How many part-files are there, and why?

The directory silver/spark/users.parquet/ contains one part-file (part-00000-...-c000.snappy.parquet, about 9.6 KB) and a _SUCCESS marker. The directory silver/spark/orders.parquet/ also contains a single part-file (about 140 KB) and a _SUCCESS marker. Spark writes one file per partition of the DataFrame at write time, because each write task produces its own file independently, which lets many tasks write in parallel. users.csv is only 7 KB, so it is read as one partition, and the narrow transformations (select, withColumn) do not change that count: one partition gives one file. For orders, the window function causes a shuffle, which could create up to spark.sql.shuffle.partitions partitions (200 by default). Adaptive query execution merges the small shuffle partitions at runtime, and the whole dataset is small, so it ends up in a single partition and therefore a single file. On a larger dataset I would expect many part-files.

Question 7: coalesce(1) before .write would produce a single file. What do you lose by doing that on a larger dataset?

You lose parallelism. coalesce(1) makes one task do all the work for that stage, on one core and one executor, instead of many writers working at the same time. That task may run out of memory or take very long. Because coalesce avoids a shuffle, it can also pull the upstream computation into that single task, which slows the whole stage. A single huge file is also worse for the readers: they can only parallelize within that file, a failed write must restart from scratch, and the object may become too big to manage. Downstream engines get less parallelism, partition pruning is lost, and you cannot append without rewriting. Several files of moderate size, typically 128 MB to 1 GB, are the better choice.

Question 8: Compare silver/orders.parquet/ and warehouse/silver/orders/. Which files hold the data, and which ones describe the table?

In silver/spark/orders.parquet/, the data is in the part-file (part-00000-...snappy.parquet). Nothing describes the table, because _SUCCESS is only a job-completion marker. The schema exists only in the footer of each Parquet file, and the “table” is simply whatever files are in the directory. In warehouse/silver/orders/, the data is in data/*.parquet, which are ordinary Parquet files. Everything else describes the table. metadata/v1.metadata.json holds the schema, the partition spec, the properties and the list of snapshots with the current one. The manifest list (snap-*.avro) lists the manifests of a snapshot. The manifest files (*-m0.avro) list the data files with their row counts and column statistics. version-hint.text tells a reader which metadata version is the current one. The table is therefore defined by its metadata, not by the files that happen to be in the folder.

Question 9: A second job overwrites the Parquet directory while a query is reading it. What does the reader see? What changes with an Iceberg table?

With a plain Parquet directory, an overwrite deletes the old files and writes new ones, and this is not atomic. The reader lists the files at planning time and reads them later. It can fail with a “file not found” error because a file was deleted, or it can read a mix of old and new files and return incomplete, duplicated or inconsistent data. With an Iceberg table, a reader works on the snapshot it resolved when the query started, so it keeps reading the old data files, which still exist, and gets a consistent result. The writer writes new data files and then commits a new metadata version in one step, so a reader sees either the old table or the new one, never a half-written state. Old files are removed later by snapshot expiration, not at commit time.

Question 10: With this catalog, the pointer to the current version of a table is a file in the bucket. What can go wrong if two jobs commit at the same time, and what would a catalog service add?

Both jobs read the current version (say v1) and each prepares v2 as its new metadata file. With a file-based hadoop catalog, the commit relies on the file system for atomic operations, which object storage does not really provide (a rename is a copy followed by a delete). One commit can overwrite the other and be silently lost, or the version pointer can end up inconsistent. The table can then be missing data that a job believes it wrote. A catalog service (REST catalog such as Polaris, JDBC, Hive Metastore, Nessie) holds the pointer to the current metadata and updates it with an atomic compare-and-swap. If the table changed since the job read it, the commit is rejected and the job retries on top of the new version, which is optimistic concurrency control. The catalog also adds a central place for access control, table discovery and consistent multi-table commits, independent of the object storage’s guarantees.
